## Phase 3: database keep-alive

Changed `backend/app/main.py` to add `GET /health/ping-db`, and added
`.github/workflows/keep-database-awake.yml` with the requested `0 0 */4 * *`
schedule and manual dispatch. The endpoint performs SELECT 1 with a 10-second
deadline. It returns 200 and a UTC timestamp only on success, otherwise 503.
It requires no login, is limited to 12 requests/minute, and logs each success.
The workflow retries cold starts and validates the JSON response rather than
accepting an unrelated HTML page with HTTP 200.

Set repository variable `BACKEND_URL` to the actual deployed backend origin.
The workflow also accepts `VITE_API_URL` and removes its `/api/v1` suffix; absent
both, it uses the repository's documented `https://flowdesk-api.onrender.com`.
That fallback URL has not been confirmed as the active deployment.

Cron day-of-month steps run on the 1st, 5th, 9th, etc.; the month boundary can
produce a shorter interval. GitHub may delay/drop scheduled runs and disables
public-repository schedules after 60 days without repository activity. Therefore,
this workflow alone cannot guarantee an indefinitely awake database. Point the
existing UptimeRobot monitor at `/health/ping-db` for independent recurring
database checks. Existing `/health` already queries the database too, but its
response is HTTP 200 even when degraded. The UptimeRobot account/target has not
been inspected or modified.
